- (event) Started mainstreamed architecture run for G.E.A.R. (create intent) on Coaching path. Input: finalized PRD (Epics 1-3, FR-1..FR-24). Greenfield — no code yet.
- (decision) Design paradigm (AD-candidate): Modular monolith with hexagonal architecture per module. Each feature module (User Directory & Auth, Tool Maintenance, Admin) is a self-contained hexagonal module exposing its own ports/adapters; modules integrate without modifying existing business logic (satisfies NFR-M1).
- (decision) Deployment shape (user refinement): NOT required to be a single docker image — may split into multiple containers/services as needed. Still one cohesive app per NFR-R1 (docker-compose) but image/container split is free.
- (decision) Database (AD-candidate): PostgreSQL. Relational for core business data (inspection history, status, qualifications) + native JSONB column for flexible attributes (FR-7/FR-10).
- (decision) Flexible attributes (AD): hybrid. First-class typed columns for all known/core attributes; a dedicated JSONB column per entity (users, tools, tool_types) holds the extension surface so new attributes need no migration (FR-7/FR-10). Future path: promote frequently-used JSONB attributes to real columns via migration while keeping the JSONB column for continued flexibility.
- (decision) Go HTTP + data layer (AD): chi router + sqlc (compile-time typed SQL via pgx) + golang-migrate (versioned migrations) + pgx driver. Boring, typed, explicit SQL supports Postgres JSONB; satisfies NFR-M2/M3 type-safety and NFR-R2 versioned migrations.
- (decision) Frontend (AD): React + Vite + TypeScript as an SPA talking to the Go JSON API. Mobile-friendly responsive; isolated Admin module as its own route/feature within the SPA. Framework settled react/vite/ts.
- (version) Verified current versions (web, 2026-08-30): go-chi/chi v5.3.2 (Aug 2026); sqlc v1.31.1 (Apr 2026); golang-migrate v4.19.1 (Nov 2025); pgx v5. Noted GO-2026-4316 open-redirect advisory is scoped to deprecated chi v2 (we use v5). React + Vite + TS latest stable.
- (decision) Auth boundary (AD): User Directory & Auth module is the single owner of users, groups, permissions, sessions, MFA. It exposes a port (Go interface) via which Tool Maintenance and Admin resolve current-user identity + resolved permission set. No other module owns auth data or duplicates permission logic. FR-19 admin isolation enforced server-side by this shared gateway.
- (decision) Tool status (AD): Status (Red/Orange/Green/Out-of-Service) is never stored — always DERIVED on read from inspection records + due-date math + the Out-of-Service flag. Single source of truth prevents UI/API drift (FR-15/FR-16).
- (decision) Deployment shape (AD): docker-compose multi-service — separate Go API, Postgres, and frontend containers (user confirmed >1 container allowed; NFR-R1/R4). Backups: configurable automated pg-based backup to >=1 destination, restore procedure documented (NFR-R3). Single-host self-hosted for the Ortsverband.
- (decision) Inspection clock (AD, user confirmed 'due date per tool'): next_due computed per tool = last successful inspection date + schedule interval (custom interval on the tool overrides the Tool Type default, FR-9). On Out-of-Service reinstatement the clock resets from reinstatement date (FR-15). Out-of-Service is a derived flag, not a due-date state. One shared rule all consumers use.
