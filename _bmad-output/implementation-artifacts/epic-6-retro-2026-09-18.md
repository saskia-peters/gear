## Findings

Grouped by aggregate view; each carries a source reference and a disposition.

### Architecture delta

- **A1 — shared derived-status clock confirmed; history premise corrected (accept).** `deriveToolStatus` (`internal/tools/core/status.go:78`) is the single shared clock: dashboard and PDF consume it through the same `dashboardStatus` wrapper (`tools.go:507`, called at `tools.go:357` for the dashboard and `tools.go:445` for the report); submit and reinstate call it directly (`inspections.go:523,525,702`). History is deliberately **not** a consumer — `ListInspectionHistory` (`inspections.go:728–825`) is a raw-record read with no status derivation or schedule resolution; the ToolDetailsPage header status is carried from the dashboard list. The "consumed by dashboard, report, and history" premise was inaccurate; the code is fine.
- **A2 — no layering violation on name resolution (accept).** The Tool module never joins user tables; inspector/actor names resolve through the narrow `DisplayNameResolver` seam (`core/tool_types.go:189–199`, implemented by the user postgres repo), one bulk `ListUsersByIDs` call for report (`tools.go:482`) and history (`inspections.go:780`). SQL comments confirm the no-join rule (`queries.sql:308–311`). **Checked and clean.**
- **A3 — minor OOS-predicate copy beside the shared function (defer, low).** `toolIsOutOfService` (`inspections.go:597–612`) re-implements the OOS rule ("latest fail at-or-after latest reinstatement") instead of reusing `deriveToolStatus`. It is a documented deliberate cheap check (one `GetToolInspectionStatus` read, no schedule resolution, no status code produced) — but a second textual copy of the predicate.
- **A4 — routing/gate structure consistent, not duplicated (accept).** All five tool surfaces are mounted once at the composition root with their own gate (`cmd/server/main.go:175,185,193,202,212`), patterns defined once in the routers (`report.go:54–60`, `tools.go:254–260`), assembled by `toolsSurface` (`main.go:243–250`). No gate or route-pattern duplication. **Checked and clean.**

### God-class / size growth

- **G1 — three Go files over the ~800 threshold (defer, tracked).** `core/tools.go` 875 lines (dashboard list, report, tool CRUD + permission/audit helpers), `core/inspections.go` **933 lines** (submit/reinstate/history/validation — the largest single file), `adapters/http/tools.go` 820 lines (all tool+inspection+history handlers + four error mappers). `report.go` (357) is healthy. Matches the standing avoid-god-class convention.
- **G2 — DashboardPage.test.tsx growth 834 → 1350 (defer, watch).** 6-1b added ~315 lines and 6-2 ~203 (the 6.2 export block alone is ~200 lines, `DashboardPage.test.tsx:1149–1350`). Test-file bloat, not shipped code, but the largest TS file in the module.

### Duplication map

- **D1 — German status vocabulary hardcoded in SummaryGrid (defer, medium).** `SummaryGrid.tsx:33,40,47` hardcodes `'Einsatzbereit'`/`'Ausstehend'`/`'Überfällig'` instead of reading `STATUS_VOCAB` from `filters.ts`; only `OOS_STATUS` is imported. `FilterChips.tsx` correctly uses the shared vocabulary, so the drift is isolated to the grid — three of four labels live outside the single source of truth `filters.ts:26–29` claims to be.
- **D2 — backend report re-declares the same German labels (defer, low).** `reportStatusLabels` (`report.go:32–37`) duplicates the four labels the SPA renders (`filters.ts:30–35`). The comment says this is deliberate so the export "never disagrees with the screen," but it is literal duplication across the Go/TS boundary with no shared constant.
- **D3 — duplicated TS status union (defer, low).** `filters.ts:23–24` defines `StatusCode` (`'oos'|'red'|'orange'|'green'`) while `auth/tools.ts:271` re-declares the identical union as `ToolStatusCode` — and `auth/tools.ts:13` already imports `StatusCode`. `DashboardTool.status` is typed `ToolStatusCode` while the filter set is typed `StatusCode`: two names for one concept.
- **D4 — near-identical date formatter in two places (defer, low).** The claimed formatTimestamp duplication between DashboardPage and ToolDetailsPage does not exist (DashboardPage renders no timestamps); instead a near-identical RFC3339→de-DE formatter with `'–'` fallback exists as `formatTimestamp` (`ToolDetailsPage.tsx:45–53`) and `formatDate` (`AdminDsgvoPage.tsx:21–28`).
- **D5 — "Deleted User" rendering centralized, not duplicated (accept).** The literal lives once as `DeletedUserDisplayName` (`inspections.go:62`) and is consumed by report (`tools.go:491`) and history (`inspections.go:796,812`); the SPA passes through the server-resolved name, pinned by a test (`ToolDetailsPage.test.tsx:324–357`). **Checked and clean.**

### Pattern divergence

- **P1 — single-code gates vs admin any-of — by design (accept).** `report.export` and `inspection.history.view` mount with `auth.RequirePermission` (`main.go:202,212`) plus a core re-check (`tools.go:401`, `inspections.go:729`), matching every other tool surface and the epic-context AD-6 "one permission per surface" decision. Admin's `RequireAnyPermission` is a different construct (any-of sets), not a divergence.
- **P2 — mount-level 403 for report/history not structured-logged (defer, low).** `RequirePermission` passes `log=nil` (`gateway.go:49`), so a non-holder blocked at the mount gate for `/report.pdf` or `/{id}/history` produces no structured log. Admin any-of gates pass a logger + German denyMsg (`admin.go:52`, `main.go:231`). The handler-level re-check mappers do log (`report.go:174`, `tools.go:639`) but that branch is rarely reached because the mount gate blocks first; uniform German 403 copy is emitted either way.
- **P3 — uniform JSON envelope + German copy confirmed (accept).** All report/history error paths write the uniform envelope: gateway 401/403 (`gateway.go:103,136`), `mapReportError` 403/500 (`report.go:171–184`), `mapInspectionError` 403/404/400/500 (`tools.go:635–660`), 404/405 handlers on every tool router. The report's success response is `application/pdf` by nature (non-JSON), hardened with `Cache-Control: no-store` (`report.go:115`). **Checked and clean.**

### Spec-to-implementation reconciliation

- **S1 — "status always derived on read, never stored" — holds (accept).** No status column exists anywhere; `migrations/000027_inspections.up.sql:8` states it verbatim; all statuses come from `deriveToolStatus` at read time. **Checked and clean.**
- **S2 — orange window proportional to the tool's own cycle — holds as evolved; frozen 6-1 text stale (fix, medium).** The rule is `window = interval * orangeWindowPercent / 100`, default 25 = one quarter of the tool's own cycle (`status.go:101`; `tools.go:127–131,722–743`); `53dd5c2` replaced the static `OrangeWindowDays = 14` constant. But frozen spec 6-1 still says "Orange ≤ 14 days" (`spec-6-1…md:52,88`) and the `DashboardPage.tsx:20–21` header comment repeats it. The deviation is human-documented in `epic-6-context.md:18` and `epic-5-retro…md:14,26,43`, yet the 6-1 spec change log does not list it.
- **S3 — "PDF reflects the currently filtered view only" — holds (accept).** The SPA builds `?status=` from the ACTIVE filter set (empty set → param omitted = "Alle") (`DashboardPage.tsx:322`; `auth/tools.ts:563–585`); the server re-derives every status and filters by the codes (`tools.go:446–449`). Pinned by tests asserting the exact `?status=red%2Corange` URL (`DashboardPage.test.tsx:1210–1260`) and the 400 path for bad codes (`report.go:84–89`, `main_test.go:1709`). **Checked and clean.**
- **S4 — "history newest-first, per-checklist-item results, Deleted User" — holds (accept).** SQL orders `submitted_at DESC, id DESC` / `created_at DESC, id DESC` (`queries.sql:314–334`); per-item results fetched in one grouped round-trip (`queries.sql:336–342`, `inspections_repo.go:194–216`); deleted accounts map to the literal via the seam (`inspections.go:796–799,812–815`); the SPA merges both lists newest-first with an id-desc tiebreak (`ToolDetailsPage.tsx:201–221`). Pinned by tests (`inspections_test.go:1149–1167,1219–1246`, `ToolDetailsPage.test.tsx:237–246,324–357`). **Checked and clean.**
- **S5 — frozen Always/Never of 6.1/6.1b/6.2/6.3 + 6.3b/6.3c intents — all hold (accept).** Verified point-by-point: 6.1 per-tool derived status with catalog-once + empty-fleet skip (`tools.go:322–361`), resilient red (`tools.go:507–527`), DTO status-only, no catalog N+1, no stored status; 6.1b one-line row + click/keyboard nav + `stopPropagation` isolation (`DashboardPage.tsx:421–514`); 6.2 gate + `ReportExportPermission` + `GetLatestInspectionByTool` (`queries.sql:283–294`) + server-only PDF (`report.go:214–256`) + no client PDF; 6.3 gate + tool-exists 404 (`inspections.go:733–742`) + seam names + schirrmeister grant migration (`000028_schirrmeister_inspection_history.up.sql`); 6.3b merged track record (`ToolDetailsPage.tsx:201–221`); 6.3c condensed cards + back button (`ToolDetailsPage.tsx:233–235,303–378`). **Checked and clean.**
- **S6 — per-tool N+1 reads accepted + documented (defer, low).** The dashboard does one `GetToolInspectionStatus` per tool (`tools.go:514`) and the report one `GetLatestInspectionByTool` per tool (`tools.go:452`); the schedule catalog is resolved ONCE per call (`tools.go:342,424`) — no catalog N+1. The per-tool reads are explicitly accepted at V1 fleet scale in code and spec (`tools.go:383–384`; spec 6-1 Design Notes L101; spec 6-2 Design Notes L91).
