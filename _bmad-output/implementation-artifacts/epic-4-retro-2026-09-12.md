## Findings

Grouped by aggregate view; each carries a source reference and a disposition.

### Architecture delta

- **A1 — clean module boundaries (accept).** Tool core imports only `adminports`/`userports` (read-only consumer ports); Admin/User never import `internal/tools` in production (verified: zero matches; the only reference is composition-root wiring `cmd/server/main.go:137`). No layering violation, no cycle. **Checked and clean.**
- **A2 — cross-module core import in HTTP adapters (accept, precedent).** `internal/tools/adapters/http/tools.go:14` and `tool_types.go:23` import `internal/user/core` for the `*usercore.User` error-mapping signature. Identical to the Admin precedent (`admin/adapters/http/backup.go:14`). Not a new violation.
- **A3 — tools core tests import Admin core to build fake ports (accept).** `internal/tools/core/tools_test.go:11` imports `internal/admin/core` for the fake `SchedulesPort`. Test-only coupling; no production cycle.
- **A4 — `DashboardViewPermission` lives in the Tool core (accept).** `internal/tools/core/tools.go:44`; the canonical catalog is `internal/user/core/roles.go:138`. A base permission's const living in a consuming module — minor ownership drift.

### Duplication map

- **D1 — UUID→pgtype.UUID parse implemented 5× with inconsistent empty-handling (fix later).** `tool_types_repo.go:329` (`parseToolTypeID`, empty→NULL), `tools_repo.go:333` (`parseOptionalUUID`, near-identical twin, different sentinel), `admin/.../schedules_repo.go:133` (empty→error), `backup_repo.go:137`, `user/.../repository.go:981`. The tools pair is the same problem twice in one package; empty→NULL (tools) vs empty→error (admin) is a behavioral inconsistency that can trip a future consumer.
- **D2 — `validateAttributes` re-implemented in tools and already diverged (defer; already recorded).** `internal/tools/core/attributes.go:80-117` vs `internal/user/core/profile.go:185-214`; the tools copy adds duplicate-key-after-trim rejection the user copy lacks. Recorded as deferred in `spec-4-4` change log.
- **D3 — `isUniqueViolation`/`isForeignKeyViolation` + `PermissionResolver`/`AuditWriter` duplicated across modules (defer).** Small, stable helpers; matches the existing admin/user pattern.
- **D4 — SPA client consolidation held (accept).** `web/src/auth/http.ts` is the single fetch site; `tools.ts`, `settings.ts`, etc. all consume `request()`/`authTokenHeaders()`. The Epic-2 action item landed and held.

### God-class / size growth

- **G1 — `AdminWerkzeugePage.tsx` 1057 lines, 4 components (accept).** Page + `ToolTypesTab` + `ToolsTab` + `ChecklistEditor`. Multi-tab page, but the two tab bodies + checklist editor are the concentrated-growth risk. The shared `AttributesEditor` was properly extracted (202 lines).
- **G2 — `tools_test.go` 1150 lines, `AdminWerkzeugePage.test.tsx` 1161 (accept).** Over the ~800-line standing convention, but single-purpose test files, not god-classes.
- **G3 — `cmd/server/main_test.go` +863 → 1183 lines (accept).** The integration mount suite; legitimately the repo's biggest test file but growing.

### Diff-scope / boundary review

- **B1 — archiving a tool type makes its tools un-editable, untested (fix).** `UpdateTool` re-validates `ToolTypeExistsActive` (`tools.go:350,429`); after the type is archived, every tool PUT answers 400 `MsgToolInvalidType` unless the type changes. Spec-4-3 allows archiving a type with active tools ("soft; list keeps showing the name") but no test covers update-of-tool-after-type-archived.
- **B2 — archiving a referenced schedule makes tool/type writes un-savable, untested (fix).** `UpdateToolType`/`UpdateTool` re-validate against active-only `SchedulesPort`. An archived default/override becomes a permanent 400. No test covers it.
- **B4 — `ToolExistsActive` parsed via `parseToolTypeID` (accept).** `tools_repo.go:206` uses the tool-TYPE-named helper (returns `ErrToolTypeNotFound`) while every other tool-id parse uses `parseOptionalUUID`. Functionally safe (error swallowed to `false,nil`) but a latent naming/sentinel confusion.
