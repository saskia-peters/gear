## Findings

Grouped by aggregate view; each carries a source reference and a disposition.

### Architecture delta

- **A1 — hexagon boundary held for the new orchestration core (accept).** `internal/dsgvo/core` imports only the module ports + `usercore` — no adapters, no SQL; `cmd/server/main.go` wires the orchestrator entirely through module services. No import cycles, no cross-module SQL writes across the 3-3/3-4 work. **Checked and clean.**
- **A2 — orchestrator imports another module's *core* (accept, convention-consistent).** `internal/dsgvo/core/dsgvo.go:21` imports `usercore` (ActorResolver `*usercore.User`, `StateDeleted`, `ErrAdminUserNotFound`) — not just the ports — which the file's own "calls each module's exported port" comment (L7-8) overstates. The same pattern pre-exists in `tools/core → admin/core` (Epic 4), so it is convention-consistent; the comment is aspirational, not false in spirit. Low.
- **A3 — misleading dead branch in the delete mapper (fix, low).** `internal/admin/adapters/http/dsgvo.go:276-281` maps `toolscore.ErrToolNotFound` to a 404 with a comment claiming a malformed target id surfaces the Tool sentinel "before the User port can answer". The orchestrator resolves actor+target via `userRepo.GetUserByID` **before** the Tool rewrite (dsgvo.go:325-342), and that repo maps a malformed id to `ErrAdminUserNotFound` — so the branch is unreachable via the delete flow and the comment mis-describes the ordering.
- **A4 — sqlc schema-scoping drift (defer).** `migrations/000029` (in the Tools sqlc block) creates a **User-owned** `sessions` index (`000029...up.sql:15-16`), contradicting the "no module's generated package carries another module's tables" claim (`sqlc.yaml:6-12`). Impact minimal (no tool query reads `sessions`), but the schema input set is no longer purely tool-owned.

### God-class / size growth

- **G1 — `AdminEinstellungenPage.tsx` is a god-class at 1572 lines (defer, tracked).** One file hosts four tab surfaces (`EmailSettingsTab` L229, `BackupSettingsTab` L525, `ScheduleSettingsTab` L946, `SystemSettingsTab` L1363); Epic 3 contributed roughly the E-Mail (~296) + Backup (~421) tabs. All Epic-3 Go files are healthy (largest `admin/core/settings.go` 547). Matches the standing avoid-god-class convention.
- **G2 — `AdminDsgvoPage.tsx` at 746 lines (watch).** Just under the ~800 flag; both 3-3 and 3-4 flows landed in it, so it is on a growth trajectory.

### Duplication map

- **D1 — duplicated permission re-check helpers (defer).** `requireAccessReportPermission`/`requireDeletePermission` are identical except the permission constant (`dsgvo/core/dsgvo.go:420-473`); the same shape recurs in the admin core (`settings.go:476-490`, `backup.go:326-340`). A shared `requirePermission(ctx, actor, code)` would collapse the four.
- **D2 — triplicated best-effort audit writers (defer).** `auditAccessReport`/`auditDelete`/`auditPurge` (`dsgvo.go:443-500`) repeat the nil-guard + warn-on-failure shape; one `audit(ctx, actor, op, detail)` helper would remove the triple.
- **D3 — duplicated "≤2000-rune mandatory reason" + German microcopy (defer).** DSGVO delete (`dsgvo.go:83-86,311-317`) and Tool reinstatement (`tools/core/inspections.go:226-229,662-666`, pre-existing) enforce the same bound with near-identical German copy. Candidate for a shared helper when the next reason-bearing story lands.

### Pattern divergence

- **P1 — orchestrator core is wire-coupled (defer).** Admin convention keeps core domain types JSON-free with HTTP-layer DTOs (`settings.go:137-147`, `backup.go:173-186`); the DSGVO orchestrator's structs carry JSON tags and the handler returns them verbatim (`dsgvo.go:141-145,252-254`). A documented divergence from the codebase's own convention.
- **P2 — delete body has no `MaxBytesReader` (fix, low).** `dsgvo.go:178` decodes the body bare; settings/backup/user all cap at 1 MB (`settings.go:84`, `backup.go:86`, `handler.go:66`).
- **P3 — malformed JSON maps to a misleading message (fix, medium).** A malformed delete body answers `"Bitte gib eine Begründung an."` (`dsgvo.go:178-180`) instead of the convention's `"Ungültiges JSON-Format."` (`settings.go:85`). A malformed body is not a missing reason.
- **P4 — divergent 400-mapping technique (defer, low).** DSGVO uses `errors.Is` + `err.Error()` (`dsgvo.go:270-271`) where settings/backup use `errors.As` on the typed error — despite the orchestrator already defining `DeleteReasonError` with `Unwrap()`.

### Spec-to-implementation reconciliation

- **S1 — frozen "Always"/"Never" sections all hold in code (accept).** Verified per story: 3-1 materialized Admin hexagon, write-only masked password, `Configured()` fallback, no caching; 3-2 ≥1-destination warning, encrypted credentials, no backup job; 3-3 read-only export, no secrets in the report, best-effort audit; 3-4 soft-delete + archive, purge as the sole hard delete, no re-activation path (tombstones excluded from `ListUsers`), `@deleted.local` reserved. All I/O-matrix rows verified in code. **Checked and clean.**
- **S2 — nil-result HTTP guards unspecified (defer, low).** `dsgvo.go:127-130,188-191` defensively answer a 500 when the service returns `(nil, nil)` — sensible and mirrors the orchestrator's nil-export guard, but appears in no spec I/O matrix.
- **S3 — stale review-order reference (fix, trivial).** spec-3-4's Suggested Review Order labels the purge route "POST purge" while the frozen section and the code use `DELETE /users/deleted/{archiveId}`.
