## Findings

Grouped by aggregate view; each carries a source reference and a disposition.

### Architecture delta

- **A1 — module boundaries held clean (accept).** Tool core imports only `adminports`/`userports` read-only consumer ports (schedules, qualifications) plus the narrow `PermissionResolver`/`AuditWriter` seams; no layering violation, no cycle introduced across 15 commits. The inspection tables (`000027`) are Tool-owned (AD-1). **Checked and clean.**
- **A2 — `inspector_id`/`actor_id` are FK-less plain uuids by design (accept, AD-8).** Migration `000027` and the DSGVO forward-compat ("Deleted User" fallback in 6.3, `inspections.go` `DeletedUserDisplayName`) rest on this; correct and documented in the migration comments.
- **A3 — status derivation is a single pure function (accept).** `deriveToolStatus` (`status.go:80`) is the one shared clock; dashboard, submit, and reinstate all consume it. The late user fix to make the orange window `interval/4` (`53dd5c2`) was a ONE-FILE change (plus tests) precisely because the derivation is centralized — the architecture paid off.

### God-class / size growth

- **G1 — `inspections.go` 863 lines (accept).** The core now holds submit/reinstate/history/validation; the history surface (6.3) was appended here. Over the ~800-line standing convention but cohesive (one inspection domain); watch on the next story.
- **G2 — `InspectionPage.test.tsx` 1360 lines (accept).** The SPA inspection surface's suite; concentrated but single-purpose. Mirrors the standing pattern of large page-test files (Dashboard 1161).
- **G3 — `internal/tools/adapters/http/tools.go` 820 lines (accept).** All tool + inspection HTTP handlers in one adapter file; crossing the ~800 convention.

### Pattern divergence

- **P1 — submit/reinstate idempotency gaps (defer, already recorded).** No idempotency key on inspection submit or reinstatement (deferred-work entries from the 5-3/5-6 reviews). The SPA double-submit guard + the OOS precondition mitigate; an explicit key would harden retried 500s. Not blocking.
- **P2 — German microcopy stayed consistent (accept).** Outcome labels, OOS consequence copy, reinstatement messages, and the status vocabulary (`Einsatzbereit/Ausstehend/Überfällig/Außer Betrieb`) held a single vocabulary across 5.2→6.1; `types/filters.ts` is the single mapping.

### Spec-to-implementation reconciliation

- **S1 — 5-2b tracked under epic-5 (accept).** Configurable system settings landed as `spec-5-2b` inside this epic's window (it was split from 5-2 for scope); the sprint-status key exists and is done. Documented, not a gap.
- **S2 — review patches densely recorded (accept).** Each story's Spec Change Log carries its review-patch trail (e.g. 5-5's response-shape guard, 5-6's OOS tie boundary, 5-4's server-authoritative consequence). The spec-as-source-of-truth convention held.
- **S3 — the 2-week-cycle "never green" defect shipped (finding, post-epic fix).** The fixed 14-day orange window (`OrangeWindowDays = 14`) made a tool whose schedule equals 14 days permanently `orange` after a pass. Reported by the user post-6.1; fixed in `53dd5c2` (window = `interval/4`). Root cause: the derivation's window was a constant, not relative to the schedule — the single shared function made the fix trivial. **Documented as a known-bad state the fix avoided.**

### Diff-scope / boundary review

- **B1 — OOS not-inspectable + reinstatement are the tightest seam (accept).** `toolIsOutOfService` + the reinstate gate + the dashboard's OOS rendering are mutually consistent (verified live: the OOS tool `GKW` renders `oos`, other tools green). No divergence found.
